# CineForge automation — unattended production, recovery and publishing

The scheduler is a separate background process (`automation/scheduler.mjs`). It does not need the dashboard to be
open. Its state lives in `logs/automation/automation.db` (SQLite, built into Node 22), so it survives dashboard
closes, crashes and Windows restarts. All commands below are for **PowerShell**, run from the `Shorts Studio` folder.

## 1. Quick start

```powershell
# 1) check health (disk, RAM, GPU, models, FFmpeg, studio, YouTube)
node automation\cli.mjs settings
# 2) choose times and topics (or use the Automation page in the dashboard)
node automation\cli.mjs set productionTime='"08:00"' publishTime='"18:00"' publishMode='"manual"'
node automation\cli.mjs set topicQueue='["Why do octopuses have three hearts?","How do vaccines train the immune system?"]'
node automation\cli.mjs set enabled=true
# 3) start the scheduler (keep this window open) …
node automation\scheduler.mjs
# … or install it to start with Windows (recommended; no admin rights needed)
powershell -ExecutionPolicy Bypass -File automation\install-startup.ps1
```

Status and control:

```powershell
node automation\cli.mjs status          # heartbeat, active runs, dead-letter queue
node automation\cli.mjs events 50       # latest events
node automation\cli.mjs runs            # recent runs
node automation\cli.mjs pause           # finish the current stage, start nothing new
node automation\cli.mjs resume
node automation\cli.mjs stop            # emergency stop: cancel the running studio job, pause
node automation\cli.mjs requeue <runId> # continue a dead-letter run from its last checkpoint
node automation\cli.mjs run-now         # one production run now
powershell -ExecutionPolicy Bypass -File automation\install-startup.ps1 -Uninstall   # stop starting with Windows
```

The dashboard's **Automation** page shows the same: heartbeat, runs with stage checkpoints, settings, health, events,
and buttons for pause / resume / emergency stop / requeue / run now.

## 2. How a run works

One run = one video, with a stable run ID across all retries:

`topic → script → render → qa → metadata → upload → publish → record`

* Every stage writes a checkpoint. A finished stage is **never redone** — after a crash, restart or retry the run
  continues at its first unfinished stage.
* **Script**: generated by the studio and validated by its gates. Unattended, only **READY** scripts are rendered
  (setting `scriptGate`). A NEEDS_REVIEW script is regenerated in the next retry slot; after the retries it waits
  in the dead-letter queue for you. FAILED scripts and known factual errors never proceed.
* **Render** uses the *saved* script version (it is not rewritten). **QA** checks the MP4 independently (ffprobe:
  video + audio streams, duration within 20 %) and stores its sha256.
* **Publish modes**: `manual` (the verified video waits for you, nothing is uploaded) · `private-upload` (uploaded
  as private) · `scheduled-public` (uploaded private with `publishAt` = the next free publish slot).
* One heavy job at a time; heavy stages (script, render) wait for free disk / RAM / VRAM and for an idle studio, and
  never start in quiet hours.

## 3. Schedule and retries

| Setting | Default | Meaning |
|---|---|---|
| `productionTime` / `productionDays` | 08:00, every day | when a run is created |
| `publishTime` / `publishDays` | 18:00, every day | publish slots (independent of production) |
| `timeZone` | Asia/Kolkata | all times; DST-safe |
| `maxVideosPerDay` | 1 | runs per production day |
| `retryCount` | 3 | retries per stage before the dead-letter queue |
| `retrySlotsMinutes` | 30, 120 | retry 1 at +30 min, retry 2 at +2 h after the first attempt; later retries in the recovery window |
| `recoveryWindow` | 13:00–16:00 | where later retries go |
| `quietHours` | 23:00–06:00 | no heavy stage starts |
| `minFreeDiskGB` / `minFreeRamGB` / `minFreeVramGB` | 15 / 3 / 3 | resource guard before heavy stages |
| `allowCatchUpPublishing` | false | overdue videos take the next free slot — never published together |

**Missed runs** (PC off at production time) run once when the scheduler starts, if missed by less than 24 hours and
only for days after automation was enabled. **Duplicates** are impossible: one run per production slot, one active
run, and a video (by run ID or sha256) is never uploaded twice.

## 4. YouTube (one-time setup)

1. https://console.cloud.google.com → create a project (e.g. "CineForge").
2. **APIs & Services → Library** → enable **YouTube Data API v3**.
3. **OAuth consent screen** → External → app name, your email → add your Google account under **Test users**.
4. **Credentials → Create credentials → OAuth client ID → Desktop app** → **Download JSON**.
5. Save it as `youtube\client_secret.json` (git-ignored).
6. Authorize once:

```powershell
node automation\youtube.mjs authorize   # opens Google's consent page; approve with the channel's account
node automation\youtube.mjs status
```

The refresh token is stored **encrypted with Windows DPAPI** in `youtube\tokens.dpapi` (readable only by your Windows
user, git-ignored); access tokens refresh automatically — no daily login. Start with `publishMode = private-upload`
on a test channel; switch to `scheduled-public` when you are satisfied.

Quota: the YouTube API allows 10,000 units/day; an upload costs 1,600. The scheduler counts units per Pacific-time
day and never starts an upload that would exceed the quota.

## 5. Recovery runbook

| Failure class | Automatic behaviour | What you do |
|---|---|---|
| Temporary network failure | exponential backoff + retry slots | nothing |
| Studio unavailable | starts the studio server, retries | if it repeats: `logs\server.out` |
| Model unavailable | retry with backoff | check System Setup → Health (Gemma model, llama.cpp) |
| Insufficient RAM / VRAM | heavy stage waits for the next retry slot | close games / other GPU apps |
| Insufficient disk | waits, retries | free space (old `projects\`, `exports\`) |
| Research failure (no topic) | retry | add topics to the topic queue |
| Script validation | regenerated in the next retry slot | after the dead-letter: review the script in Script Studio, then `requeue` |
| Voice / visual / render failure | retried from that stage (script kept) | check the studio job log in Job History |
| Upload interrupted | resumes from the byte Google confirmed | nothing |
| YouTube quota exhausted | waits for the next quota day | nothing (or reduce videos/day) |
| YouTube OAuth failure | **not retried** — dead-letter + notification | `node automation\youtube.mjs authorize`, then `requeue` |
| Retries exhausted | dead-letter + Windows notification | fix the cause, `requeue <runId>` |

Nothing that failed QA, or any stage, is ever uploaded or published.

## 6. Files and security

* Machine settings (ports, file locations, log level, notifications) are in `.env` — see `.env.example`; loaded and validated by `dashboard/lib/config.js`. Schedules, retries and publishing stay in the automation database (Automation page), not in `.env`.
* Before committing: `node tools/check-secrets.mjs` (optional pre-commit hook: `git config core.hooksPath tools/git-hooks`).

* `automation\` — scheduler code · `logs\automation\automation.db` — state (backed up daily to `logs\automation\backups\`, 7 kept) · `logs\automation\scheduler.out` — process output when started by Windows.
* Secrets: `youtube\client_secret.json` and `youtube\tokens.dpapi` are git-ignored; the token is DPAPI-encrypted.
* The studio API listens on 127.0.0.1 only; the scheduler talks to it locally.
